## Architecture

Use a **modular monolith**.

Apply Clean Architecture principles where they provide clear value, but do not over-engineer.

Do NOT:

* create microservices
* create a generic repository pattern
* introduce MediatR/CQRS everywhere without a clear reason
* create excessive interfaces
* add Azure services yet
* add event buses yet

The goal is a clean foundation that can evolve later.

## Multi-Tenancy

Multi-tenancy is one of the most important architectural requirements.

Every tenant-owned entity must contain TenantId.

The authenticated user determines the TenantId.

Never accept TenantId from normal tenant-owned client requests.

The JWT should contain at least:

* sub → UserId
* tenant_id → TenantId
* role → UserRole
* email

Create a current-user abstraction such as:

```csharp
public interface ICurrentUser
{
    Guid UserId { get; }
    Guid TenantId { get; }
    string Email { get; }
    UserRole Role { get; }
}
```

Create an HTTP implementation that reads claims from the authenticated request.

Do not allow client-provided TenantId to override this context.

## Registration

Create:

POST /api/auth/register

Request:

```json
{
  "businessName": "Bruno's Cafe",
  "businessType": "FoodAndBeverage",
  "branch": {
    "name": "Main Branch",
    "code": "MAIN",
    "addressLine1": "Odiongan",
    "addressLine2": null,
    "city": "Odiongan",
    "province": "Romblon",
    "postalCode": "5505"
  },
  "owner": {
    "firstName": "Ace",
    "lastName": "Agas",
    "email": "owner@example.com",
    "password": "SecurePassword123!"
  }
}
```

Registration must happen within one database transaction.

Create:

1. Tenant
2. Branch
3. Owner User

If any operation fails, rollback all changes.

Never allow partially registered tenants.

Validate:

* business name required
* valid supported business type
* branch name required
* branch code required
* owner first name required
* owner last name required
* valid email
* password complexity
* duplicate email
* DiagnosticCenter unavailable

If DiagnosticCenter is submitted, return a clear domain/application error such as:

```json
{
  "code": "BUSINESS_TYPE_NOT_AVAILABLE",
  "message": "Diagnostic Center support is coming soon."
}
```

## Login

Create:

POST /api/auth/login

Request:

```json
{
  "email": "owner@example.com",
  "password": "SecurePassword123!"
}
```

Response:

```json
{
  "accessToken": "...",
  "expiresAtUtc": "...",
  "user": {
    "id": "...",
    "tenantId": "...",
    "tenantName": "Bruno's Cafe",
    "businessType": "FoodAndBeverage",
    "firstName": "Ace",
    "lastName": "Agas",
    "email": "owner@example.com",
    "role": "Owner"
  }
}
```

Use secure password hashing.

Prefer ASP.NET Core's PasswordHasher or another reputable implementation.

Do not implement custom cryptography.

JWT configuration must come from environment/configuration.

Do not hardcode secrets.
