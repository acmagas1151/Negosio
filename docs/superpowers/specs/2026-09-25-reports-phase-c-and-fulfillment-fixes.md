# Spec: Fulfillment recovery fixes + Reports Phase C (Branch/Register/Cashier performance)

**Branch:** `feature/pos-for-delivery` (recreated from `master` at `80147ea` — the prior fulfillment-simplification branch of the same name was merged to `master` and deleted in an earlier session).

**Scope-protection note, repeated throughout this spec and its plan: do not merge to `master`, do not push any branch.** All work stays local on `feature/pos-for-delivery` until the user decides otherwise.

This spec covers two small, already-diagnosed bug fixes to the whole-sale fulfillment model (built by the prior `2026-09-19-simplify-fulfillment` plan, now on `master`), followed by a new reporting feature, Reports Phase C. Both fulfillment fixes were investigated in full before this spec was written — no further discovery is needed, only implementation. Reports Phase C's metric definitions below were derived directly from reading the actual current Reports module and domain model, not invented; every definition below cites the exact existing convention it reuses or extends.

## Part 1: Fulfillment fixes

### 1A — Recovery path for a failed post-checkout schedule call

**Problem.** Checkout (`POST /api/pos/checkout`) and schedule creation (`POST /api/sales/{id}/delivery-receipts`, `POST /api/sales/{id}/pickups`) are two separate API calls. `PosTerminal.tsx` fires the second immediately after the first succeeds, for Delivery/Pickup checkouts. If the second call fails, the sale is left `Completed`, paid, with `SaleItem.DeliveryRequiredQuantity`/`PickupRequiredQuantity` set, but with **no** `DeliveryReceipt` row. The error toast tells the cashier to "schedule it from the sale's detail page" — but Sale Detail's Fulfillment section only renders when `summary.deliveries.length > 0 || summary.pickups.length > 0`, so in this exact failure state it renders nothing at all. Worse, `SaleFulfillmentCalculator.Derive(null, null)` returns `TakeNow`, so the sale's own status badge actively mislabels a paid Delivery/Pickup sale as Take-now.

**What already exists and must be reused, not rebuilt:**
- Backend endpoints `POST /api/sales/{id}/delivery-receipts` and `POST /api/sales/{saleId}/pickups` already exist and require no item list — they resolve "every item on this sale" themselves.
- Frontend `fulfillmentApi.createDelivery(saleId, body)` / `createPickup(saleId, body)` already exist in `web/negosio-web/src/api/fulfillment.ts`, used today only from `PosTerminal.tsx`.
- The "at most one active schedule per sale" guard in `DeliveryReceiptService.CreateScheduleAsync` (a post-lock `hasActiveSchedule` check, throwing `ErrorCodes.DeliveryReceiptNotAllowed`) already makes a retry from Sale Detail safe against creating a duplicate schedule — **no new backend guard is needed for this fix.**
- `FulfillmentDetailsFields.tsx` (the flat Take-now/Delivery/Pickup form component built by the simplification plan) already renders exactly the fields a create-schedule form needs (date, recipient, address-for-delivery, contact, notes) — reuse it, do not build a new form component.

**Required behavior:**
1. On Sale Detail, when a sale's items indicate a delivery or pickup was required (`deliveryRequiredQuantity > 0` or `pickupRequiredQuantity > 0` on any sale item — already returned by `GET /api/sales/{id}`) but `summary.activeSchedule` is null (no `DeliveryReceipt` exists yet, or none is non-cancelled), show a distinct "Needs delivery scheduling" / "Needs pickup scheduling" state — **not** the generic Take-now label, since that's actively wrong here. Determine this state client-side from data already returned; no new backend field is required.
2. In that state, render a "Schedule now" action that opens the existing schedule-creation form (reusing `FulfillmentDetailsFields.tsx`) and calls `fulfillmentApi.createDelivery`/`createPickup` directly — the exact same call `PosTerminal.tsx` already makes.
3. On success, refresh the Fulfillment section so the new schedule appears immediately (standard react-query invalidation).
4. On failure (e.g., a race where a schedule was created in another tab in the meantime, surfacing `ErrorCodes.DeliveryReceiptNotAllowed`), show a clear error and refresh — do not let the cashier believe the retry silently failed with no explanation.
5. Update the post-checkout error toast in `PosTerminal.tsx` if its current wording ("schedule it from the sale's detail page") needs adjusting once the actual affordance exists — verify the instruction is accurate, don't leave a toast pointing at a UI that still doesn't fully match its description.

**Explicitly out of scope:** making checkout and schedule-creation a single atomic server-side transaction. That would be a much larger, riskier change; the two-call design is being kept, only its failure recovery is being fixed, matching how this was scoped when the issue was first found.

### 1B — Voiding a sale strands its pending schedule

**Problem.** `VoidSaleService.VoidAsync` has zero awareness of fulfillment schedules — voiding a sale with an active Pending `DeliveryReceipt` leaves that schedule Pending and orphaned. Reports already exclude voided sales (confirmed: every delivery/pickup/fulfillment report query filters `Status != SaleStatus.Voided`), so the schedule silently disappears from every operational report — but it is not blocked from further action: `CompleteAsync` (the shared method behind Mark-Delivered/Mark-Claimed) never checks the parent sale's status at all, so a Pending schedule on a voided sale can still be marked Delivered/Claimed. Meanwhile `LoadFulfillableSaleAsync`'s status gate (`Completed`/`PartiallyRefunded`/`Refunded` only) blocks the *cancel* path for a voided sale's schedule, since every current `CancellationDisposition` (`DeliverLater`, `PickupLater`, `ConvertToDelivery`, `ConvertToPickup`, `CustomerPickedUpInstead`) requires a replacement schedule, which requires passing that gate. Net effect: staff can complete a stranded schedule but cannot cancel it through the normal UI once its sale is voided.

**Required behavior:** voiding a sale with an active (non-cancelled) fulfillment schedule must cancel that schedule automatically, atomically, as part of the same void transaction — with a clear, distinct audit trail (not silently deleted, not mistaken for a cashier-initiated cancellation).

**Design, reusing existing machinery (confirmed available by investigation):**
- Add a new `CancellationDisposition` value (e.g. `SaleVoided`) representing "the sale was voided; this schedule is released with no replacement." None of the 5 existing values fit — all assume a replacement schedule is created, which is wrong here (there's no sale left to fulfill).
- Route this new value through `CancelWithDispositionAsync`'s existing `buildReplacement: null` branch. This branch is already fully wired and currently dead code (no live caller passes null today) — it already skips `LoadFulfillableSaleAsync`'s Completed-only gate and does a plain untracked sale read instead, which is exactly the behavior needed for a sale that is about to become (or already is) Voided. No structural changes to `CancelWithDispositionAsync` should be needed beyond adding the new enum value to its validator's allowed-dispositions lists (`DeliveryReceiptValidators.cs`) — scoped so `SaleVoided` is only ever set by the void code path, never selectable by a cashier through `CancelFulfillmentModal.tsx`'s disposition dropdown.
- `DeliveryReceipt.Cancel(...)` already records reason/disposition/actor/timestamp for any cancellation — reuse it as-is. Use a clear system-generated reason text (e.g. "Sale voided" plus the void's own reason if available) and the voiding user as the actor.
- `FulfillmentConversion`'s existing shape already supports a same-method (`fromMethod == toMethod`), no-replacement (`replacementRecordId: null`) audit row — no schema change needed there either. Record one, with a reason describing that the sale was voided.
- **Transaction/locking discipline:** `VoidSaleService.VoidAsync` opens one transaction and takes one pessimistic lock today (`RegisterSessions WITH (UPDLOCK, HOLDLOCK)`) before its authoritative re-check and its only write. The fulfillment cascade must run inside this same transaction. Because `DeliveryReceiptService`'s own create/cancel paths serialize against concurrent operations via a `SaleItems WITH (UPDLOCK, HOLDLOCK)` lock (`LockSaleItemsAsync`), the void path must take the equivalent lock before reading/cancelling any `DeliveryReceipt` for the sale, to stay consistent with how concurrent schedule operations are already serialized elsewhere and avoid a race between "void cascades cancel" and "cashier cancels/creates a schedule" happening at the same moment. Get the lock ordering right relative to the existing `RegisterSessions` lock to avoid introducing a deadlock — investigate current lock-acquisition order across `VoidSaleService` and `DeliveryReceiptService` before deciding which lock to take first.
- A sale can have at most one active schedule (the whole-sale invariant), so at most one `DeliveryReceipt` needs cancelling per void — this is not a batch/loop operation.
- Confirm (by reading `CompleteAsync`) that it already requires `FulfillmentStatus.Pending` as a precondition, so once the cascade flips the schedule to `Cancelled`, Mark-Delivered/Mark-Claimed naturally can no longer act on it — closing that half of the inconsistency without a separate code change. If `CompleteAsync` does NOT already gate on `Pending` status, that gap must also be closed as part of this fix.

**Explicitly out of scope:** re-deriving report visibility (already correct — voided sales already excluded everywhere) and any change to how Voids or Returns work generally. This is a narrow, additive cascade.

**Global constraint for both fixes:** review the existing cancellation and conversion rules (`CancelWithDispositionAsync`, `DeliveryReceiptValidators.cs`, the 5 existing dispositions) before changing anything — do not weaken the whole-sale invariant (one fulfillment method for every item, at most one active schedule per sale, ever). The new `SaleVoided` disposition must not become a second way for a cashier to bypass that invariant; it is reachable only from the void path.

## Part 2: Reports Phase C — Branch, Register, and Cashier performance

### Conventions to reuse without modification (confirmed exactly as follows by reading the current code)

- **Filter contract:** `ReportFilter(Period, FromDate, ToDate, BranchId, RegisterId, CashierId)` already exists and already carries all three of Phase C's scoping dimensions — no new filter contract needed. New endpoints bind `[FromQuery] ReportFilter`, same as Overview/TopProducts/Categories.
- **Date/timezone resolution:** `ReportPeriodResolver` already resolves any `ReportPeriod` (including `Custom`) into UTC instant bounds using a fixed Manila `UTC+8` offset (`BusinessOffset`, no DST — a deliberate, documented v1 simplification), plus a "previous period of equal length" comparison range. Reuse `ReportPeriodResolver.Resolve(...)` exactly as Overview does; do not write a second timezone conversion anywhere in Phase C's new code.
- **Branch scoping:** every new query must call the existing `IBranchAccessResolver.ResolveListFilterAsync(filter.BranchId, ...)` before any other filter, exactly as `ReportsService.BaseSalesAsync`/`BaseReturnsAsync` already do. For Owner/Admin this returns the requested branch or `null` (tenant-wide/all branches). For Manager it silently forces the caller's own assigned branch, ignoring any requested value — this is enforced service-side and must not be bypassable by a client-supplied `branchId`. A Manager viewing the new Branch-performance report will therefore only ever see their own single branch's row; this is correct, expected, existing behavior, not a bug to fix.
- **Authorization:** put every new endpoint on the existing `[Authorize(Policy = AuthorizationPolicies.ReportsView)]` class-level policy on `ReportsController` (Owner/Admin/Manager only). This spec does not ask for Cashier self-service reporting — "Cashier performance" means Owner/Admin/Manager reviewing a cashier's numbers, the same audience as every existing report.
- **Aggregation style:** LINQ-to-EF translated to server-side SQL (SUM/COUNT/GROUP BY), never raw SQL strings, never full materialize-then-aggregate-in-memory except where the codebase already documents a specific, narrow exception (the `GetDeliveryFulfillmentAsync` status-derivation case) — Phase C should not introduce a new such exception without an equally explicit justification comment.
- **Pagination/bounding:** use `PagedResult<T>.CreateAsync(...)` on an `IQueryable` (server-side `Skip`/`Take`) for any report that returns "a list of branches/registers/cashiers" that could plausibly grow past a page — the same pattern `GetDeliveriesAsync`/`GetPickupsAsync` already use. Do not materialize an unbounded per-entity list into memory.
- **Split-tender payments:** aggregate by *payment record*, not by sale — a split-tender sale contributes once to each payment method's total, matching `ComputePaymentMethodsAsync`'s existing behavior. Apply the same convention if any Phase C view breaks down payment methods per branch/register/cashier.
- **Distinct-sale aggregation:** where a metric could otherwise double-count a sale that joins to multiple rows (e.g. multiple payments, or historical multi-schedule sales from before the whole-sale simplification), aggregate over a `.Select(...).Distinct()` on sale id first, exactly as `GetDeliveriesAsync`'s charge-total computation already does — do not sum a joined result set directly if the join can multiply rows per sale.
- **DTO/type conventions:** every new backend DTO field mirrors 1:1 into a camelCase TypeScript type in `api/types.ts`, exactly as every existing Reports DTO does. Every figure is a backend-computed aggregate; the frontend never recomputes a total from raw rows.
- **Frontend filter/table conventions:** reuse `useReportFilters` (URL-synced period/date/branch/register/cashier state) and, for any list-shaped result, `usePagedQuery` composed the same way `FulfillmentReportsPage.tsx` already composes both hooks. Reuse the `Table`/`Table.HeaderCell` (with `sortKey` for sortable columns — this is a supported-but-currently-idle capability in the shared `Table` component; Phase C is the first consumer to actually turn sorting on), `Pagination`, `EmptyState`, `ErrorState`, `SkeletonText` conventions used everywhere else in Reports. Reuse `ReportFilterBar.tsx` for the date/branch/register/cashier filter row; extend it only if a genuinely new filter is needed (it should not be).
- **Charts:** Recharts, following `SalesTrendChart.tsx`'s conventions (CSS-var colors, `isAnimationActive={false}`, custom tooltip component, `EmptyState` fallback when all values are zero) for any comparison chart across branches/registers/cashiers.

### Metric definitions (exact, derived from the current Overview implementation — do not diverge without a documented reason)

These reuse the Overview module's own documented formulas, just grouped by branch/register/cashier instead of aggregated tenant/branch-wide:

- **Gross sales** = Σ `Sale.Subtotal` (before discount, before tax) for qualifying sales in the range.
- **Discounts** = Σ `Sale.DiscountTotal`.
- **Net sales** = Σ `Sale.GrandTotal` (after discount/tax; note this also folds in `DeliveryCharge`, a pre-existing, already-documented revenue-classification quirk in the Overview module — Phase C inherits it rather than fixing it, to stay consistent with the number the Overview page already shows for the same sales).
- **Returns** = Σ `SaleReturn.TotalRefund`, attributed to the **return's own date**, not the original sale's date — same as Overview.
- **Net collected** = Net sales − Returns.
- **Average sale** = Net sales ÷ completed-transaction count, `0` when count is 0 (never divide by zero) — same rounding convention (`Money.Round`) as Overview.
- **Qualifying sales** = `CreatedAtUtc` within the resolved range AND `Status != Voided` — same `Qualifying(...)` predicate Overview already uses, reused directly, not reimplemented.
- **Void activity** = count and value of sales with `Status == Voided` and `VoidedAtUtc` within the range (attributed to the *void's* date, not the sale's original creation date — same as Overview's `VoidedSalesCount`/`VoidedSalesValue`), grouped by branch/register/cashier. Show both the **actor** (`Sale.VoidedByUserId`) and, distinctly, the **approver** (`Sale.ApprovedByUserId`, null when the actor voided directly under their own authority) — this attribution is already fully persisted and must not be conflated into one field.
- **Return activity**: same actor/approver distinction, using `SaleReturn.CreatedByUserId` (actor) and `SaleReturn.ApprovedByUserId` (approver, null when acted on direct authority).
- **Discount activity**: report the **amount and count only** (`Sale.DiscountTotal` aggregated, count of sales with a non-zero discount). **Do not report who approved a discount** — investigated and confirmed: the discount approver's identity is verified at checkout time (`IApproverVerification`) but is never persisted anywhere on `Sale` or `SaleItem`. This is a genuine, pre-existing data gap, not something to invent a value for. Document this explicitly as a known v1 limitation in the final report, exactly the same way the existing Overview module already documents its own known limitations (e.g. the product/category live-join quirk) rather than fabricating a field. If the user wants discount-approver reporting in the future, it requires a new persisted column and migration — flag it as a follow-up, do not build it speculatively now.

### Branch performance

- One row per branch (Owner/Admin: every branch in the tenant; Manager: their own single assigned branch only, per existing `BranchAccessResolver` behavior).
- Columns: Net sales, Gross sales, Transaction count, Average sale, Discounts, Returns (count + value), Void activity (count + value, with actor/approver visible on drill-down, not necessarily in the summary row).
- "Useful comparison across branches" = a sortable table (sort by any numeric column) is sufficient; a comparison bar chart (Recharts, one bar per branch per metric) is a reasonable enhancement but the sortable table is the load-bearing requirement.
- Drill-down: each branch row should link to that branch pre-selected in the existing Overview report (`ReportFilterBar`'s branch filter, URL-synced) where richer detail (trend chart, payment breakdown, top products) already exists — do not duplicate that detail inside the Branch performance view itself.

### Register performance

- **No existing per-register aggregation report exists today** (confirmed: `RegisterId` is currently only a *filter*, never a *group-by*, on any report) — this view is genuinely new, not an extension of something already partially built.
- One row per register (scoped to the resolved branch filter — a register belongs to exactly one branch).
- Sales/transaction measures: same Net sales / Gross sales / transaction count / average sale as Branch, grouped by `RegisterSessions.RegisterId` via the same join pattern `ReportsService.BaseSalesAsync` already uses for its `RegisterId` filter (`s.RegisterSessionId` → `RegisterSessions.RegisterId`), just grouped instead of filtered.
- Payment-method breakdown per register: same split-tender-safe, per-payment-record aggregation as Overview's `ComputePaymentMethodsAsync`, grouped by register.
- Cash in/out: Σ `RegisterCashMovement.Amount` grouped by `Type` (`CashIn`/`CashOut`), joined through `RegisterSessionId` → `RegisterId`, for sessions/movements within the resolved range.
- **Register-session reconciliation, "where the existing data supports it":** a `RegisterSession`'s `ClosingCash`/`ExpectedCash`/`CashDifference` are computed once, at close time, and persisted directly on the session row (`RegisterSessionService.ReconcileAndCloseAsync`) — there is no service that recomputes or re-derives these after the fact, and no existing mechanism to split a session's reconciliation figures proportionally across a midnight boundary. **Do not invent a day-proportional split.** Report **closed sessions as individual rows** (one row per closed `RegisterSession` that falls in the range, dated by its `ClosedAtUtc` business-local date), showing its already-computed `OpeningCash`/`ClosingCash`/`ExpectedCash`/`CashDifference`/breakdown fields verbatim. A session still `Open` at query time is either excluded from the reconciliation sub-view or shown as "still open, no reconciliation yet" — do not attempt to compute a live reconciliation figure for an open session; that number does not exist until close.
- A register report should therefore likely be two related views/tabs, matching the "sales measures" vs. "session reconciliation" distinction above: an aggregate sales/payment/cash-movement table grouped by register (day-range-aware, using the sale-level `Qualifying` predicate), and a list of individual closed sessions with their persisted reconciliation figures (session-row-aware, not day-bucketed at all). Do not force these two fundamentally different granularities into one table.

### Cashier performance

- **No existing per-cashier aggregation report exists today** either (same situation as Register — `CashierId` is a filter only) — genuinely new.
- One row per cashier, attributed via `Sale.CreatedByUserId` (confirmed: this is the actual field behind every "cashier" filter/display in the codebase, despite DTOs elsewhere naming it `CashierUserId` — there is no separate cashier-identity field to discover). Note that `Sale.CreatedByUserId` can belong to any role that completed a checkout (Cashier, Manager, Owner, Admin all can ring up sales under their own identity) — "Cashier performance" in practice means "performance by whoever completed the checkout," not strictly `User.Role == Cashier`. Do not filter the report to `Role == Cashier` only; that would silently hide a Manager's or Owner's own checkout activity from the same report a user would expect to show every till operator.
- Columns: Net sales, transaction count, average sale, discounts (amount/count only, per the discount-approver limitation above), returns (actor = the cashier who processed the return, approver shown distinctly), void activity (actor = the cashier, approver shown distinctly).
- **Multi-branch scenario, reframed per investigation:** a `User` has at most one current branch (`User.BranchId`, a single nullable scalar) — there is no multi-branch assignment table, and a cashier cannot be simultaneously assigned to two branches today. The verification scenario "a cashier assigned to more than one branch" as literally stated cannot occur under the current schema. The realistic, testable equivalent: a cashier's `BranchId` is reassigned partway through the reporting period (e.g. transferred from Branch A to Branch B). Verify that each of the cashier's *historical sales* remains attributed to whichever branch was actually recorded on that `Sale` at checkout time (`Sale.BranchId`, set once, never retroactively changed) — i.e., changing a user's *current* branch assignment must never retroactively reattribute their *past* sales to the new branch. This is the actual risk worth testing, and the spec's verification section below uses this reframed scenario instead of the impossible one.
- Drill-down: link each cashier row to the existing Overview report pre-filtered to that cashier (`cashierId` param, already supported by `useReportFilters`) for deeper detail — do not duplicate a trend chart per cashier inside this view.

## Part 3: Verification requirements

Both fulfillment fixes and all three Phase C reports must be verified with the following representative cases (adapt from the user's original request, reframed per the investigation findings above where the original scenario was factually impossible under the current schema):

- **Split tenders**: a sale paid with 2+ payment methods must contribute once per method to any payment-method breakdown (Register view), and once, at its full `GrandTotal`, to Net sales (Branch/Register/Cashier).
- **Discounts**: a discounted sale's discount amount must appear correctly in Branch/Cashier discount totals; confirm no approver identity is fabricated or left silently blank in a way that implies data exists when it doesn't (i.e., the UI should not show an "Approved by: —" for discounts if that implies a real-but-missing value — prefer omitting an approver column for discounts entirely, or labeling it clearly as not tracked).
- **Partial and full returns**: a partially-returned sale must still count at its original value in Gross/Net sales for its branch/cashier, offset by its Return in the same or a different period depending on the return's own date, exactly as Overview already behaves — confirm Phase C's grouped figures reconcile with Overview's tenant-wide figures for the same date range (sum of all branches' Net sales == Overview's tenant-wide Net sales for the same filters, modulo the Owner/Admin-sees-all vs. Manager-sees-own-branch access difference).
- **Voids**: a voided sale must appear in its branch/cashier's void count/value (attributed to the void's date), be excluded from that branch/cashier's Net/Gross sales for the range it was *voided* in (per the existing `Qualifying` exclusion), and correctly distinguish actor vs. approver.
- **Cash movements**: a session with both Cash In and Cash Out movements must show both correctly in the Register view, matching the same figures `RegisterSessionService.ReconcileAndCloseAsync` already computed at close time (cross-check the report's numbers against the session's own persisted `CashDifference` — they must agree, since both should derive from the same underlying `RegisterCashMovement`/`Payment`/`SaleReturn` rows).
- **Sessions crossing midnight**: a session opened before and closed after local midnight must appear as a single row in the closed-sessions reconciliation view (dated by `ClosedAtUtc`'s business-local date, per this spec's design decision above — do not attempt to split it), while its individual sales still bucket correctly into whichever business day each sale's own `CreatedAtUtc` actually falls in for the sales-aggregate view.
- **Multiple branches**: an Owner/Admin viewing Branch performance sees every branch; a Manager sees only their own — confirm this is enforced server-side (attempt to pass a different `branchId` as a Manager and confirm it's ignored/forced back to their own branch, not merely hidden client-side).
- **Cashier branch reassignment** (reframed scenario, see above): verify a cashier's historical sales keep their original `Sale.BranchId` attribution after the cashier's own `User.BranchId` changes.
- **Fulfillment fix 1A**: simulate a checkout succeeding followed by a schedule-creation failure (e.g., by triggering the one-active-schedule guard artificially, or another reproducible failure path); confirm Sale Detail shows the "needs scheduling" state (not a false Take-now label) and that using the new recovery action successfully creates the schedule; confirm a second, redundant attempt (retry) does not create a duplicate schedule (the existing guard should reject it cleanly, and the UI should handle that rejection gracefully).
- **Fulfillment fix 1B**: void a sale with an active Pending Delivery and, separately, a sale with an active Pending Pickup; confirm in each case the schedule is automatically cancelled with the new `SaleVoided` disposition, a `FulfillmentConversion` audit row is recorded, the schedule can no longer be marked Delivered/Claimed, and the sale continues to be correctly excluded from delivery/pickup reports (already-existing behavior, just confirm it still holds).
